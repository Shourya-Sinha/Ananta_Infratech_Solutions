# Ananta Infratech Solutions — Platform

Monorepo for the construction workforce & project management platform. See
`ananta-architecture.md` (in the parent chat) for the full architecture,
schema, permission matrix, API contract, and roadmap.

## Stack

Plain JavaScript everywhere — **no TypeScript, no YAML, no pnpm**.

- **Package manager**: npm workspaces (native, no pnpm/turbo)
- **Backend** (`services/api`): Node.js + Express, plain CommonJS `.js`
  files, MongoDB/Mongoose, Redis, Socket.IO
- **Admin Web** (`apps/admin-web`): React 18 + Vite, plain `.jsx`, Tailwind CSS
- **Mobile** (`apps/mobile`): **Expo (managed workflow)**, plain `.jsx`,
  React Native Reanimated for real animations, no native `android/`/`ios/`
  project folders needed for development
- **Shared packages** (`packages/*`): plain `.js`, consumed by all three
  apps via npm workspace symlinks
- **No CI/CD YAML**: instead, `npm run verify` at the repo root runs lint +
  test + build locally, meant to be run before every push
- **No docker-compose YAML**: `infra/docker/start-dev-services.sh` starts
  MongoDB + Redis with two plain `docker run` commands

### Why plain JS instead of TypeScript

This was originally built in TypeScript and converted to plain JavaScript
on request. The conversion was done mechanically (Babel's TypeScript-strip
transform across all 154 source files) rather than hand-rewritten, then
verified: every backend file passes `node --check`, the full Express app
(`app.js`, all 17 modules) was confirmed to `require()` cleanly with real
Node module resolution, all four shared packages load and execute
correctly, and both frontend builds succeed with the exact same output
size as before conversion. The backend specifically uses CommonJS (not
native ESM) because Node's ESM loader requires explicit `.js` extensions
on every relative import — CommonJS avoids that whole class of bugs and is
the simpler, more traditional setup for a plain Express app.

One byproduct worth knowing about: the backend's `module.exports` lines
were generated by an automated codemod, so some files export via
`exports.ServiceName = { ... }` with auto-generated internal variable names
in a few spots — functionally identical to hand-written CommonJS, just not
hand-styled.

**Real bugs found and fixed during the Expo → bare RN → Expo round trip**
(each confirmed via an actual Metro/Expo bundle, not just by inspection):
- Metro couldn't resolve `@babel/runtime` or any hoisted package inside
  this npm workspace — fixed with monorepo-aware `watchFolders`/
  `nodeModulesPaths` in `metro.config.js`.
- The `@/` import alias used in every file needs Metro's own
  `resolver.resolveRequest` hook, not a Babel plugin — Metro's dependency
  graph reads raw import strings via a lightweight static scan *before*
  Babel plugins run, so `babel-plugin-module-resolver` has no effect on
  actual bundling despite working in isolated tests. Proved this the hard
  way with a direct `@babel/core` test before finding the real fix.
- Moving back to Expo, `expo export:embed --entry-file node_modules/expo/AppEntry.js`
  failed because that path doesn't exist locally — npm hoists `expo` to
  the *workspace root* `node_modules` in this monorepo, not
  `apps/mobile/node_modules`. Worse, even pointing directly at the hoisted
  file still failed: `AppEntry.js` does `import App from '../../App'`,
  a path relative to wherever the file *physically* sits, which resolves
  to the wrong directory entirely once hoisted. Fixed the standard way for
  Expo + monorepos — a local `index.js` entry point that imports
  `registerRootComponent` from `expo` and `./App` directly, sidestepping
  the fragile relative path inside the hoisted file.
- That same bundle attempt then failed with a Flow-syntax parse error
  inside `react-native/index.js` — traced to npm having silently installed
  **two different react-native versions** (`0.74.5` at the correct location,
  a stray `0.87.1` nested under `expo`'s own dependency tree), which Expo
  51's Babel/Flow parser config doesn't understand. Fixed with a
  `"overrides": { "react-native": "0.74.5" }` entry in the root
  `package.json`, forcing one consistent version workspace-wide — the
  standard fix for this exact class of monorepo duplicate-dependency bug.
- Backend push notifications had been switched to Firebase Cloud Messaging
  during the bare-RN phase (since Expo push tokens don't work outside
  Expo) — reverted back to Expo's push API (`exp.host`) now that the app
  is Expo again, which is simpler and needs no Firebase project.

**How this was verified** — and the honest limit of that verification:
this sandbox has no Android SDK, Xcode, or physical device, so the app was
never actually run and tapped through. What *was* verified: a real
`expo export:embed` bundle for **both** platforms completed successfully,
each confirmed to contain the actual app code (registration screens,
gradient/animation components, etc. — not a stub), `eslint` passes clean,

### Worker self-registration — added, was previously a dead end

Previously the mobile app only let a **Manager** register a worker (Add
Worker screen); there was no path for a worker to register themselves,
and — this was the real bug underneath the missing UI — even the API
couldn't complete self-registration end to end:

- `POST /workers` (work-type selection, registration Step 2) required the
  `worker.create` permission, which WORKER accounts never hold by default
  — only Managers/Admin have it. So even a worker who somehow got a login
  session had no way to finish creating their own profile.
- `registerStart` set an unknown, randomly-generated placeholder password
  with no way for the worker to ever learn it or set their own — there was
  no real path from "OTP verified" to "can actually log in."

Both fixed:
- Registration now takes the worker's own chosen password directly
  (`registerStartSchema` gained a `password` field), removing the
  placeholder-password dead end.
- Added `POST /workers/me` — a self-service version of work-type selection
  scoped to the caller's own account, same record-level-scope principle as
  the `/workers/me/documents` self-upload route from earlier.
- **Closed a security gap this change would otherwise have introduced**:
  setting your own password at registration means nothing gates login on
  actually having verified the phone number. Added a `phoneVerified` flag
  on `User`, set `true` only after a successful `REGISTRATION`-purpose OTP
  verification, and `login()` now rejects with `PHONE_NOT_VERIFIED` if it
  isn't set — checked *after* password validation, not before, so a
  wrong-password attempt can't be used to probe whether a number is
  verified. Admin-created accounts (Managers, the seeded Super Admin) are
  marked `phoneVerified: true` at creation time, since they're vouched for
  by the creating admin directly rather than needing OTP.
- `register/start` also now allows a clean **resend** for an account that
  exists but never finished OTP verification (updates name/password,
  reissues the OTP) instead of hard-blocking with a conflict error —
  otherwise anyone who left the app mid-registration would be
  permanently stuck.

Mobile side: a real `AuthNavigator` stack (Login + Register — `LoginScreen`
previously had no navigation context to link anywhere), a `RegisterScreen`
with a two-step form→OTP flow that auto-logs the person in right after
verification, a `SelectWorkTypeScreen` for the post-login "you're logged
in but have no profile yet" state, and a `WorkerOnboardingGate` that
checks for that state and shows the right screen automatically. Verified
via a real Metro bundle on both platforms (Android + iOS) with the new
screens confirmed present in the compiled output — not just linted.

### Two real backend bugs found and fixed earlier in development
- `GET /workers` and `GET /attendance` didn't scope results for the
  WORKER role — any worker account could list the entire company roster
  or every worker's attendance history. Fixed with proper record-level
  scoping (`/workers/me`, forced `worker=self` on attendance queries).
- `POST /workers/:id/documents` required the `worker.create` permission,
  which WORKER accounts never hold — so a worker literally couldn't
  upload their own documents. Fixed with a self-service
  `POST /workers/me/documents` route. That fix initially had an Express
  routing-order bug (`/me/documents` registered after the `/:id/documents`
  wildcard, so `:id` would greedily match "me" first) — found and fixed
  by inspecting route registration order directly.

### Troubleshooting

- **`[vite] API unreachable` / red "API server isn't reachable" banner:**
  the backend on port 4000 isn't answering. Start it (`npm run dev:api`),
  then check (a) MongoDB/Redis containers are up
  (`docker ps` should list `ananta-mongo` + `ananta-redis`), (b) `.env`
  exists at the repo root (copy `.env.example`), and (c) the API
  terminal for the `❌ Invalid environment configuration` message, which
  names the exact missing variable.
- **`403 Forbidden` on materials / equipment / site-diary (or any route
  that used to work):** the database was seeded before that permission
  key existed. Just restart the API — every boot gap-fills missing
  permission rows automatically without touching admin-customised
  toggles (see `services/api/src/db/syncPermissions.js`). Re-running
  `npm run seed` is equally safe and does the same fill.
- **Music player "Scan folder / drive" finds nothing:** pick the folder
  that directly holds your music (open the drive, then choose a folder
  inside it — browsers can't select a bare drive letter like `D:`).
  "Add songs" works file-by-file as a fallback.
- **Reports → Export CSV downloads an error/blank page:** fixed — export
  now goes through the authenticated client. If you still see it, hard
  refresh (`Ctrl+Shift+R`) to drop the cached bundle.
Log in with the seeded Super Admin (`SEED_SUPER_ADMIN_PHONE`/`SEED_SUPER_ADMIN_PASSWORD`
from `.env`, default `9999999999` / `ChangeMe123!` — change this
immediately in any real deployment) on the admin web app. The mobile app
is for MANAGER/WORKER accounts only.

## Salary, RBAC, Site Finance & Payment Receipts (latest)

**Salary calculation (audited & fixed)**
- Formula (unchanged, now verified end-to-end): attendance → daily earning
  `(hours ÷ full-day hours) × daily rate`, overtime beyond the threshold at
  the overtime multiplier → ledger → monthly rollup
  `Net = Gross + Overtime − Advance − Kharchi − Other`.
- Fixed: attendance reversals stored the *pre*-reversal running balance, so
  the ledger balance never dropped after a correction/delete.
- Fixed: advance deductions were dated to the *request* date — they now land
  in the month the money is **paid**; a deduction whose month is already
  FINALIZED/PAID is carried into the current open month, never silently
  written into a locked month. Deductions are idempotent per request (a
  retried approve/pay can never deduct twice).
- Fixed: reversals now net against gross earnings (not "other deductions"),
  so the payroll sheet's gross matches the actual attendance.
- Fixed: `PRESENT` with no hours = full day, `HALF_DAY` with no hours = half
  day (previously both earned ₹0). `hoursWorked + overtimeHours ≤ 24` enforced.
- Site finance no longer **double-counts** advance/Kharchi: they are paid out
  of the worker's gross salary, so site cost = other expenses + gross salary
  (payouts are still reported separately as cash already paid).

**Per-worker salary rates (hour / day / month)**
- Manager/Admin sets ONE basis via `PUT /salary/worker/:id/salary-rate`
  (`salary.rate.manage`); `@ananta/utils deriveSalaryRates` derives the other
  two (monthly = daily × `WORKING_DAYS_PER_MONTH`, default 26; hourly =
  daily ÷ full-day hours). Falls back to the work-type daily rate.
- `GET /salary/worker/:id/preview` and `GET /salary/me/preview` return the
  derived rates, **today's salary**, month-so-far totals, and the
  **approximate monthly salary** (projected + for monthly-salaried workers
  the fixed monthly amount) minus deductions — shown on the worker's home
  screen and the manager's Set Salary Rate screen. Rate changes only affect
  attendance posted afterwards.

**RBAC — who can do what**
- A **worker can never mark or correct attendance** (hard check in the
  service, not just a permission key) and never their own. **Manager** marks
  attendance only for workers assigned to a site they manage; **Admin** any
  site. Attendance delete is Super-Admin only.
- Mobile: `SUPER_ADMIN` now gets the Admin navigator (previously fell into
  the worker onboarding flow), Manager gets the Manager navigator, Worker
  gets the worker app (view-only attendance).
- Admin Web (`apps/admin-web`) is **Super-Admin only** — `ProtectedRoute`
  now rejects Worker/Manager accounts with an "Admin access only" screen.
- New permissions: `salary.rate.manage`, `salary.receipt.manage`,
  `site.billing.manage` (auto-synced to existing DBs on API boot).

**Per-site finance & monthly billing**
- Admin sets a site's monthly client billing: `PUT /finance/site-billing`
  (`{ siteId, month, billedAmountRupees, receivedAmountRupees? }`).
- `GET /finance/site/:id/dashboard?month=YYYY-MM` (Manager: own site only):
  billing vs received/pending, worker gross salary, advance+Kharchi already
  paid out, salary still payable, other expenses, admin investment, profit/
  loss on billed and on received, plus a **daily approximation** (average
  cost/day, projected month cost and projected profit/loss).
  `GET /finance/overview?month=` gives every site + company gross (Admin).
  Shown in Admin Web Finance (select a site) and the mobile Site Finance
  screen.

**Salary payment receipts + OCR**
- After finalizing, Admin marks a worker paid with the UPI/bank receipt:
  `POST /payroll/:month/workers/:workerId/mark-paid` (multipart: `file`
  image + `transactionId`, `ocrText`, `note`). The image is stored via
  ImageKit as a `PAYMENT_PROOF` document; the worker sees the receipt under
  **Salary → Salary payment receipts** in the mobile app (`GET /salary/me/receipts`).
- Small OCR extractor (`services/api/src/modules/payroll/receiptOcr.js`):
  paste the receipt text (from phone OCR) into `POST /payroll/receipts/ocr-preview`
  — or pass it as `ocrText` with the upload — and it extracts **amount,
  date, time and UPI transaction ID/UTR** with a confidence score. Both the
  OCR result and the admin-confirmed values are saved on the
  `SalaryPaymentReceipt` record. (Image→text itself is client-side; the
  parser is the deterministic, unit-tested part and a server OCR engine can
  be plugged in front of `parseReceiptText` later.)

- **Site details fully editable**: client, project type, start date, expected completion, budget, manager, description and status can all be set at site creation or via **Sites → Details → Edit**; choosing "Unassigned"/empty clears them (nullable PATCH). Unassigned sites also get a one-click **Assign manager** control in view mode, and empty manager lists link straight to manager registration. Assigning validates the account is really a Manager/Admin.

## Work type vs per-day wage (latest)

In **Add Worker**, the **Work type** dropdown now shows only the trade name (Mason, Foreman, Carpenter…) — no money in the dropdown. The wage is a **separate "Per-day wage (₹/day)" field**: picking a work type pre-fills its standard rate as a suggestion, and the admin overwrites it with the worker's **actual agreed daily rate** (the real-world rate, which differs per worker). The wage is saved on the worker profile (`salaryMode=DAILY`, `dailyRateRupees` on `POST /workers/register`) and drives salary from day one; it can later be changed in Salary. Worker Detail shows the wage as "(agreed rate)", or "(work-type standard…)" when no individual rate was set.

## Editing the per-day wage later (Worker Detail → Per-day wage & salary calculation)

The registration wage is not locked in. **Worker Detail** now shows a **Per-day wage & salary calculation** panel: current per-day / per-hour / approx. monthly rates, rate source (worker's agreed rate vs work-type standard), month-so-far earnings, projected gross and approx. monthly net — all from `GET /salary/worker/:id/preview`, the same `deriveSalaryRates` engine used by attendance posting, statements, payroll and site finance. Super Admin can **edit the per-day wage inline** (live preview: ₹/day → ₹/hour ÷8 → ₹/month ×26 as they type) and save via `PUT /salary/worker/:id/salary-rate`. New rates apply only to attendance posted afterwards — past ledger entries, statements and paid payrolls are never rewritten, so historical finance stays exact. Calculation chain is covered by `tests/unit/perDayWageCalculation.test.js` (full/half day, overtime, mixed-month net after advance + Kharchi, agreed-rate precedence, edited-rate re-derivation).

## Real-time finance updates over WebSocket (latest)

Every money-moving edit now takes effect **immediately on every connected screen** — no reloads. The API emits one unified `finance:updated` event (plus the specialised `salary:rate_updated` / `site:billing_updated` events) from a single helper (`emitFinanceUpdate`) wired into: per-day wage set at worker registration and later wage/rate edits, attendance post/correct/delete (earnings), advances & Kharchi (create/approve/reject/pay), site investments/income/expenses/capital, **site billing** (previously had no socket event), company expenses, payroll finalise and mark-paid. Events fan out to the admin room, the affected site's room (manager + assigned workers) and the affected worker's room. **Admin Web** listens once in AppShell (`useFinanceSocketSync`) and refreshes all finance/payroll/salary/advance/Kharchi/worker/site queries (250 ms burst-coalescing, so bulk attendance marking doesn't storm the server). **Mobile** now actually connects its socket (`FinanceSocketSync` in App.jsx) and refreshes salary/finance data live for managers and workers. Emission is fire-and-forget: a down socket can never fail a financial mutation.

## Preview close button + joining-date salary period (latest)

## Payroll shows hours + per-day calculation (latest)

The Payroll **Attendance** column no longer shows a bare cryptic `1P` (a status count that looked like a full paid day). It now reads in words with actual hours — e.g. **"1 Present · 6h worked"**, "1 Absent (AB)", including overtime. This matters because a PRESENT day marked for **6 hours at ₹750/day pays 6 × ₹93.75/hr = ₹562.50 (shown ₹563)**, not ₹750. Each payroll row's **Days & ledger** drill-down (and the Worker page salary statement) now has a **day-by-day attendance table**: every date shows AB, 1h, 2h, 6h, 8h Full day, Half day, Paid leave or `8h + 2h OT`, the exact calculation (`6h × ₹93.75/hr = ₹562.50`, OT with its multiplier), and that day's payable amount before deductions. Powered by a shared `describeAttendanceDay` helper (`@ananta/utils`) used by `GET /salary/worker/:id/statement` (`dailyAttendance` + `salaryRates`), with `totalHoursWorked` stored on MonthlyPayroll at Calculate-month time. Covered by `attendanceDayPayExplanation.test.js`.

## Every paise exact — no nearest-rupee rounding (latest)

Display rounding previously hid paise: the Payroll rate header showed **₹94/hr** (₹93.75 rounded up) and a 6h day showed **₹563** instead of **₹562.50**. Money was always stored as exact integer paise, but the Admin/mobile formatters rounded displays to whole rupees, and one approve-advance path rounded the actual approval amount. Now: the central `formatINR` formatters (Admin Web + mobile) always render exactly 2 decimals, every display-side `Math.round(.../100)` was removed (payroll totals, day pay, finance, requests, salary panel, worker detail, budgets, materials), advance approvals send the exact rupee amount (₹562.50, not ₹563), and the backend continues to store/pay integer paise (`netSalaryPaise` is paid as-is). Covered by `exactPaiseMoney.test.js`.
